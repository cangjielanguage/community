# 社区成长路径



## 1. 角色定义

| **角色**                  | **描述**                                                     |
| ------------------------- | ------------------------------------------------------------ |
| 用户  (Users)             | 使用 Cangjie项目的广大用户，以Issue形式向仓颉社区反馈问题和功能建议。 |
| 贡献者  (Contributors)    | 有一定代码编程经验的开发者。Contributors以参与仓颉社区代码贡献、文档贡献、技术方案讨论及设计、解答用户问题、发表技术文章及视频课程、组织策划仓颉社区活动等形式参与仓颉社区。 |
| 提交者  (Committers)      | Committer拥有Team子领域的代码仓写权限。Committer 负责Team领域软件模块设计与评审，负责代码审核及维护，处理仓颉社区的issue、邮件列表问题，辅导Contributors快速理解Team领域架构设计并提升代码开发技能。 |
| Team负责人（Team Leader） | Team  Leader负责特定Team的运营及维护。Team Leader负责定义特定Team的工作范围及业务目标，并负责对应Team的运营及维护；吸纳并发展Committer参与对应Team的项目孵化、文档完善及社区推广；定期在PMC项目管理委员会汇报Team孵化项目及Team运营进展，并基于PMC的指导建议完成相关改进。 |
| PMC  成员 (PMC)           | 项目管理委员会（PMC）成员，仓颉新版本发布、Roadmap发布、新PMC/Committer等社区事务的投票权、以及新的 PMC 成员和 Committer 提名权。PMC负责仓颉社区的管理工作，包括仓颉社区版本规划、竞争力规划、补丁规划等；组织PMC委员的选举和退出，负责Committer的任命和退出；负责仓颉社区Team的申请准入、孵化项目指导、毕业项目准入和生命周期管理等。 |

## 2. 晋升机制和流程

### 2.1 晋升机制简介

#### 2.1.1 如何成为Contributor

普通社区用户通过认领issue的方式提交PR，贡献代码，被Committer合入后即可成为Contributor。

#### 2.1.2 如何晋升Committer

优秀的仓颉社区贡献者，经现任PMC/Committer提名和投票后，可以成为仓颉社区Committer，Committer按照权限可分为Approver审批人和Reviewer审阅人。

#### Approver审批人：

- 仓颉项目贡献至少3个月
- 至少10个PR的主要审阅人
- 至少有30个PR的审核意见或30个实质性的代码PR提交
- 对所申请的仓库代码非常熟悉
- 由对应仓库的审批人或Team Leader或PMC提名

#### Reviewer审阅人：

- 仓颉项目贡献至少2个月
- 至少有5个PR的主要审阅人
- 至少有10个PR的审核意见或10个实质性的代码PR提交
- 对所申请的仓库代码非常熟悉
- 可以由对应仓库的审批人或审阅人提名

具体细节请查看：[如何晋升committer](https://gitcode.com/EricHaHaHaHa/community/blob/main/zh/committer_nomination_and_withdraw.md)
#### 2.1.3 如何成为Team Leader

优秀的仓颉社区 Committer，通过PMC项目管理委员会批准后，可以成为对应的Team的Team Leader。

- 新申请Team的Team Leader： 任何开发者可以在社区中寻找2-3个有共同兴趣及目标的开发者，确定Team Leader候选人，通过PMC项目管理委员会发送新建Team的PR申请，经PMC项目管理委员会批准后，可以成为此新Team的Leader。
- 已有Team的Team Leader： 已经是对应Team所看护领域的仓库Committer，可以由对应Team的Committer、Team Leader或PMC成员提名。

#### 2.1.4 如何晋升PMC成员

优秀的仓颉社区Committer，经现任PMC成员提议和投票后，可以成为仓颉社区PMC。

### 2.2 晋升Committer投票流程

2.2.1 由现任PMC/Committer提名，以标题“[VOTE] New Committer [Approver/Reviewer] xxx”发送邮件至 **仓颉PMC官方邮箱**。

2.2.2 所有PMC成员有权通过“+1”或“-1”形式表示支持或反对，PMC通过回复邮件发送投票结果，投票时间一般持续72个小时。

2.2.3 提名Approver权利的Committer获得四票及以上赞成票，无反对票情况下投票通过。投反对票的PMC成员必须说明反对的具体问题（无问题描述的反对票无效），投票发起人可针对具体问题进行澄清或修复。

2.2.4 提名Reviewer权利的Committer获得三票及以上赞成票，无反对票情况下投票通过。投反对票的PMC成员必须说明反对的具体问题（无问题描述的反对票无效），投票发起人可针对具体问题进行澄清或修复。

2.2.5 投票通过后，**PMC主席在仓颉社区公告新Committer**。

### 2.3 晋升PMC投票流程

2.3.1由现任PMC提名，并在PMC会议上进行投票决策。

2.3.2 被提名的PMC候选人，在获得2/3及以上的参会PMC成员赞成下投票通过。有投票权的到会PMC成员超过应到会PMC成员的一半，会议方为有效。

2.3.3 投票通过后，**PMC主席在仓颉社区公告新PMC成员**。

### 3. PMC主席任命

**PMC主席**由仓颉项目群技术指导委员会任命与罢免。

## 3. 非活跃成员退出标准和流程

### 3.1 非活跃成员定义

#### 3.1.1 非活跃Committer:

连续6个月以上没有在仓颉社区参与代码审核、PR提交、设计评审等。

#### 3.1.2 非活跃Team：

连续3个月以上未召开Team小组会议，连续6个月以上没有在PMC项目管理委员会汇报孵化项目及运营进展。

#### 3.1.3 非活跃PMC成员：

连续3个月以上未参与PMC会议，连续6个月以上没有在仓颉社区参与代码审核、PR提交、设计评审、社区活动推广等。

### 3.2 非活跃成员退出流程

#### 3.2.1 非活跃成员退出有两种方式:

| 序号 | 退出方式                                                     |
| :--- | ------------------------------------------------------------ |
| 1    | 1.PMC主席自己或委托PMC成员审视并收集非活跃成员名单；<br/> 2.PMC会议不定期审视非活跃成员名单，并对不活跃成员进行退出投票，在获得2/3及以上的参会PMC成员赞成下投票通过。有投票权的到会PMC成员超过应到会PMC成员的一半，会议方为有效。 <br/>3.PMC主席自己或委托PMC成员对投票通过的待退出不活跃成员进行退出处理。 |
| 2    | 1. 非活跃成员自发邮件申请退出，邮件标题采用“Inactive [Committer/Team Leader/PMC] xxx”，并发送邮件至仓颉PMC官方邮箱；<br>2. PMC主席自己或委托PMC成员对申请退出的非活跃成员做退出处理。 |
